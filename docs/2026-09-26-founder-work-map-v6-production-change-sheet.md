# Founder Work Map V6 生产变更单

## 目标

- 让手动查询投递不再被最长数分钟的 Codex 分析阻塞。
- 把工作地图改成“业务线 / 基础设施 → 项目 → 子项目、任务、阶段目标”的树形结构。
- 把 `给静姐和 Kenny 哥 update` 识别为 A 线任务，不占项目编号。
- 把 `企业微信接入` 识别为 `AiJia 合伙人对齐室` 下的探索期子项目。
- 把 `飞书第一阶段目标` 识别为 `AiJia 合伙人对齐室` 的阶段目标，不占项目编号。
- 合并重复的 `团队对齐智能体项目`，并恢复已由 Ivy 确认的 Smart Listing 方向。
- 人工确认过的工作地图基线优先于后续模型摘要；新表达保留为待确认建议，不静默覆盖当前方向。

## 精确前置条件

- 生产数据库：`topics=40`、`perspectives=34`、`relations=33`。
- 目标 topic ID、版本与 `deploy/founder-work-map-v6-20260926.manifest.json` 完全一致。
- Bridge 健康，批准群不变，群自动发送仍保持关闭。
- 任何计数、版本或目标 ID 漂移：停止，不 apply，不自动回滚。

## D2 执行顺序

1. 创建一致性 SQLite 备份并验证 `integrity_check=ok`。
2. 停止 Bridge，确认无正在执行的 worker lease。
3. 部署已经通过完整测试的应用镜像；保持现有 secret、模型与功能开关。
4. 对数据库副本执行 V6 baseline preview；确认预计产生：5 个 canonical version 更新、1 个 `same_as`、3 个 `part_of`，无新 topic。
5. 在生产数据库 apply 同一 manifest。
6. 启动 Bridge，验证 `/health`、`/ready`、容器状态、数据库完整性和队列状态。
7. 只读生成真实 V6 工作地图预览，在 Codex 中交给 Ivy review；不发送飞书群。
8. Ivy review 通过后，另行执行第一次受控群内发送。

## 验证重点

- `查看待对齐` 在 Founder 分析进行中仍能由独立投递循环响应。
- 工作地图先显示 A 线、B 线、公司协作基础设施，再显示其项目树。
- 项目编号连续；任务与阶段目标不占编号。
- 群聊来源不展示内部 `om_...` ID；历史观点在总览中只显示数量，详情通过 `查看对齐：项目名` 查询。
- `Smart Listing` 当前方向为已确认的单套房源智能入口方向。
- `团队对齐智能体项目` 不再作为独立项目。
- `企业微信接入` 位于合伙人对齐室下，状态为 exploring。

## 异常处理

- 任一前置断言、迁移、baseline preview/apply、健康检查或完整性检查失败：先停止并保留现场，不自动回滚。
- 不自动继续重试未知失败；先输出安全错误类别和失败阶段。
- 只有 Ivy 明确决定后才执行回滚或继续修复。

## 清理

- 删除部署归档、构建目录和一次性预览副本。
- 保留当前一致性数据库备份和审计日志；不保留多余 app 目录副本。
