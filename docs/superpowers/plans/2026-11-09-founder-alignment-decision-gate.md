# 新版分歧卡上线方案

> 本文保留 2026 年 11 月 9 日的设计与验收计划，供维护规约引用分类规则；实际完成状态以对应发布与验收记录为准。业务代码实施和生产切换按项目授权分别推进。实施时可用 `superpowers:executing-plans` 按验收步骤执行。

**目标**　飞书「查看分歧」既能回看双方考虑过的不同判断，也能快速看到当前确实需要确认的事。

**实现方式**　沿用现有群聊证据、Space 快照、分歧候选及结论记录，在生成卡片和处理编号回复时检查同一条决策准入规则。飞书文字卡和白板共用分类结果。

**技术栈**　TypeScript、SQLite、Vitest、现有飞书卡片与白板。沿用现有持久化结构和分析通道。

**产品样例**　租后场景的必要判断见下方“租后样例”。历史新旧对照 HTML 作为本地评审附件留存。

## 分类与展示

| 情况 | 卡片怎么显示 |
| --- | --- |
| 口头探讨、未立项想法，或有不同看法但当前没有明确要定的事 | **讨论记录**。如果能核对双方对同一问题确有不同判断，列入独立的 **真实分歧** 栏并标「留档」。保留当时的理由、日期和来源。 |
| 议题已经进入实际决策，仍有具体问题待确认 | **待确认**。列要定的事、它影响的实际动作及明确提出确认的来源。有双方分歧时，同时展示两方理由。 |
| 只有一方表达，或两边谈的范围、日期不同 | 归入原有「缺少另一方表达」或历史记录。只有另有同一事项的明确决策请求时，才可列该请求为待确认。 |
| 已有结论、撤回或暂停 | 已有结论按现有记录展示，保留确认人。撤回或暂停的事项回到历史，保留原始资料。 |
| 等第三方回函、资料或核实结果 | 归项目卡点。只有内部已明确提出需要决定一项实际动作时，才将该内部决策列入待确认。 |

**待确认的准入条件**　同一事项的可追溯材料同时写明「现在要确认的具体选择或边界」和「确认后会改变哪项实际工作」。接受白名单群里经身份核对的当事人发言，或当前已同步项目正文里的明确待确认项。以引用所对应的原文为准。仅凭模型的 `candidate`、栏目名「待决定」、项目整体已立项、日期临近、无人回应，均不能取得编号。实际决策可以是是否启动某项工作，立项前也可以有明确的决策请求。

首版识别原文中直接写出的请求。群聊接受「请确认／请决定／本轮需要确定」开头的具体请求，并要求同一发言说明会影响的实际工作。Space 接受同样的请求，或当前「待确认」段落里逐项写清的选择和工作影响。例如「请确认首轮比较是否加入 Amy 提出的取舍，确认后才能定验收范围」。对只说「这个以后可以看看」「这个还待确认」或转引旧话的条目，保留在讨论记录。上线前在离线预览列出因证据不足留档的旧条目，核对是否漏掉明确的现行请求。采用这项保守规则的代价是，含蓄表达的实际决策有可能暂时只出现在记录里。

**租后样例**　显示「讨论过的分歧 · 口头交流 · 未立项」。Ivy 倾向从中介可能更容易接受的小场景切入。James 更看重行业理解、实际业务价值和现有流程。两方理由标「项目页转述」，注明 10 月 11 日讨论与出处。该事项在「真实分歧」栏显示留档，不生成编号、待确认项或下一步。

**展示顺序**　第一栏显示真实分歧的数量和事项，有内容时在白板高亮；第二栏显示待确认，之后是讨论记录、缺少另一方表达、已确认共识、最近已解决及「资料截至」。真实分歧为零时显示「0 项／无」。同一真实分歧进入实际决策时，在真实分歧中保留双方理由，也在待确认中列待决定的问题和处理编号。正文与可编辑白板对同一事项采用同一分类。长理由在白板展示摘要，在文字卡保留可追溯的理由和出处。可定位原话时才用引号并注明发言人、日期与消息或文档位置，转述直接注明来源。实际决策可以缺少另一方意见，卡片只展示已知表达。

## 实施与验收

### 1. 用原始证据判定是否进入决策

- [ ] 在 `founder-manual-query.ts` 收拢群聊分歧候选和 Space 条目的分类入口，提取可复用的判定函数。群聊通过 `ContextSourceRepository` 查 `actionConsequence` 对应证据、群、发言身份及实际发生时间，核对同议题和当前请求。Space 通过 `space-project-page-view.ts` 回查最新可用快照，使用 `pageBlocks` 按 `blockId` 核对摘要摘录与原段。只有两条准入条件均能在原文定位时返回可处理项。判断必须基于实际发言或正文，识别格式限定在直接请求和项目正文中明确的逐项说明。
- [ ] 保留既有历史候选、快照、确认记录和 ID。旧数据按同一规则读出。旧标题本身不足以保留编号，现有原文足够时可继续编号。来源缺失、指向其他事项、已撤回、已被后续结论替代，或只能读到过期版本而无法证明仍待定时，保留记录并标来源情况。
- [ ] 用 `tests/alignment-judgement.test.ts` 和 `tests/space-project-page-view.test.ts` 覆盖无实际请求的租后条目、项目已立项但某议题只在讨论、明确当前选择且有实际影响、只有一方提出的实际请求、历史引用、第三方答复和同一段多个事项。群聊首版沿用现有候选入口，单方请求可通过当前 Space 正文进入待确认。另验后续已有结论不会重新打开旧议题。

### 2. 对齐卡片、白板与编号回复

- [ ] 修改 `founder-manual-query.ts` 的「查看分歧」「查看待对齐」和带项目名的查询。带项目名目前走 `buildTopicAlignment`，仍保留它的双方观点和历史，并用同一规则显示当前待确认。项目进展卡的「待决定」使用同一判定，避免同一议题在不同入口被当成两种状态。卡片只有正文有足够证据的待确认项才进入 `alignmentRefs`，讨论记录不占编号。
- [ ] 在 `alignment-judgement-service.ts` 写入前复核该引用仍符合准入条件。群聊使用现有 issue ID 和版本，Space 使用项目、段落 ID 与当前正文。旧卡引用变成留档或原文已改时，提示刷新并保留原记录。沿用既有回复事务与重复投递保护。一个 Space 段落包含多个独立待确认项，或混有会被同一旧引用一并关闭的其他事项时，显示该议题但暂不提供编号，等对应来源有独立条目再开放回复。
- [ ] 在 `founder-whiteboard.ts` 将真实分歧放在第一栏，有内容时高亮；待确认放第二栏，讨论记录放第三栏。此渲染器也被日报和周报调用，分歧卡的高亮通过分歧视图显式传入。沿用现有配色、白板和文本输出。
- [ ] 用 `tests/founder-manual-query.test.ts`、`tests/alignment-judgement.test.ts` 和 `tests/founder-whiteboard.test.ts` 验证所有入口口径一致。覆盖租后条目不计待确认、一个实际待确认项能按原编号处理、已归档的旧卡编号不能写入、重复回复不重复记账、同段多事项无法被一次回复误关闭、理由与来源在卡片可读，以及日报和周报白板没有出现分歧高亮。

### 3. 离线验收与生产切换

- [ ] 在经确认的实际开发工作树完成实现后运行 `TMPDIR=/tmp npm test -- tests/founder-manual-query.test.ts tests/alignment-judgement.test.ts tests/founder-feedback-router.test.ts tests/founder-whiteboard.test.ts tests/space-project-page-view.test.ts`，再跑全量测试、`npm run typecheck`、`npm run build` 和 `git diff --check`。
- [ ] 用隔离本地数据生成可审阅的新旧文字卡与白板。逐项核对租后留档、合成实际决策可编号，以及已有结论和缺少另一方表达保留其原意。用已有本地快照做一次旧分类对照，列出降到留档的旧条目与原因。交付候选提交、离线输出和测试结果后，另出锁定版本的生产变更单。
- [ ] 获生产授权后，核对实际部署版本、健康、待发送状态和报告队列。选避开 18:00 采集、日报周报及在途工作的窗口，保留上一版镜像、配置和一致性 SQLite 备份，部署锁定版本并按变更单重启 Bridge。验收版本、健康、留存数据与报告配置，用已批准的只读方式核对。群内实际验收另约明确的触发与投递范围。
- [ ] 如果卡片错误生成待确认、旧回复能误写、健康检查失败或投递状态不明，停止验收并记录证据。按变更单约定恢复前一版应用镜像，是否允许额外重启在生产变更单中列明。现有记录随库保留，避免用整库恢复覆盖期间新增的消息和回执。

本方案的审批范围是产品规则与实现设计。代码实施需按项目 `AGENTS.md` 获 Ivy 批准，生产变更以候选提交和明确切换窗口另行审批。
